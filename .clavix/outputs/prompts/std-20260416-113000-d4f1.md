# Improved Prompt

# Bug: Sesión no persiste tras login exitoso

## Síntoma
Tras un login exitoso en la webapp (Nuxt 4 + Dexie + endpoint externo
de SEMS/UNAM), la primera petición posterior al backend retorna 401
y el usuario es redirigido de vuelta a /login. El login doble
(login → login otra vez) hace que funcione, lo que sugiere que
la primera sesión queda en un estado inválido pero no se detecta.

## Objetivo
Diagnosticar la causa raíz antes de aplicar cualquier fix. El
"login doble" es un workaround; queremos entender por qué la
primera sesión no queda utilizable y corregir eso.

## Pasos para reproducir
1. Logout completo (asegurar que no hay sesión activa en IndexedDB).
2. Login con credenciales válidas → se marca como exitoso.
3. Navegar a cualquier vista que haga petición al backend
   (/descargar, /comprobantes, etc.).
4. Observar: redirige a /login.

## Hipótesis a verificar (en orden)
1. **Race condition auth.global.ts**: el middleware ejecuta
   checkSession() antes de que authService.login() termine de
   escribir la sesión en IndexedDB.
2. **sessionToken no se adjunta en el primer request**: el login
   devuelve token pero http.service no lo toma hasta que haya
   otra lectura de IndexedDB.
3. **Re-auth interceptor se dispara y falla**: http.service
   intercepta el 401 pero al re-leer credenciales cifradas el
   descifrado falla (deviceSecret race?) y ejecuta logout.
4. **Backend externo requiere warmup**: el token expira si el
   primer request llega demasiado pronto o sin algún header.
5. **sessionToken con typo/formato incorrecto**: el token
   guardado no es el mismo que el backend espera en el header
   Authorization.

## Archivos relevantes a inspeccionar
- `app/services/auth.service.ts` (login flow + storage)
- `app/services/http.service.ts` (interceptor 401 + re-auth)
- `app/middleware/auth.global.ts` (guard de rutas)
- `app/composables/useSession.ts` (estado reactivo)
- `app/db/schema.ts` (`Session.lastError`, `last401At` — ¿se llenan?)

## Diagnóstico pedido
1. Agregar logs temporales en los 5 puntos de arriba para
   identificar en qué paso falla.
2. Inspeccionar `sessions.lastError` y `last401At` en IndexedDB
   después de un login "fallido" para ver el error real.
3. Comparar qué cambia entre el login 1 y el login 2 en
   `authSecrets` / `sessions`.
4. Verificar en Network tab si el primer request posterior
   lleva el header `Authorization` y con qué token.

## Entregable
- Causa raíz identificada y explicada con evidencia (logs o
  valores en IndexedDB).
- Fix dirigido a esa causa (no "login doble" como atajo).
- Si el login doble sigue siendo la única solución viable,
  documentar por qué y qué está bloqueando un fix limpio.

## Criterios de éxito
- Un login exitoso basta para hacer peticiones sin redirigir a /login.
- El interceptor 401 (http.service) sigue funcionando para renovar
  sesiones expiradas en el futuro.
- No se introduce el "doble login" como comportamiento permanente.
- `sessions.isActive = true` y el token se usa desde el primer
  request post-login.
